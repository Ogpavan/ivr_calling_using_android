Android call-audio policy inspection (selected, redacted)
==========================================================

Target: vivo/iQOO I2403, Android 16/API 36, MediaTek MT6878

1. Telephony device ports

Port ID 12: "Telephony Tx"; AUDIO_DEVICE_OUT_TELEPHONY_TX
  PCM 16-bit: 44100, 48000 Hz; channel mask 0x0001
  PCM 32-bit: 44100, 48000 Hz; channel mask 0x0003

Port ID 18: "Voice Call In"; AUDIO_DEVICE_IN_TELEPHONY_RX
  PCM 16-bit: 8000, 16000, 32000, 44100, 48000 Hz
  channel masks 0x000c, 0x0010 (policy-declared input profiles)

2. Uplink mix port

IOProfile: "incall_music_uplink"
  flag: AUDIO_OUTPUT_FLAG_INCALL_MUSIC (0x10000)
  PCM 16-bit: 44100, 48000 Hz; channel mask 0x0003
  PCM 32-bit: 44100, 48000 Hz; channel mask 0x0003
  supported device: Port ID 12, Telephony Tx
  maxOpenCount=1; maxActiveCount=1

3. Audio routes

Mix; Sink: "Telephony Tx"
  Sources: Built-In Mic, Built-In Back Mic, Wired Headset Mic,
            BT SCO Headset Mic, USB Device In, USB Headset In,
            incall_music_uplink

Mix; Sink: "voice tx"
  Sources: Voice Call In

The first route is a genuine internal playback-to-telephony-uplink route, not an
acoustic speaker/microphone path.

4. Call-assistant routing

Supported system usage: AUDIO_USAGE_CALL_ASSISTANT
CALL_ASSISTANT strategy selected device: AUDIO_DEVICE_OUT_TELEPHONY_TX

5. Current idle state

The dump showed an audio patch from mix port 11 (incall_music_uplink) to device port 12
(Telephony Tx), owned by the system telephony UID. The incall music output reported
Global active count 0, so no active call or active injection was being tested.

Conclusion: static hardware/policy evidence is positive for digital uplink routing.
It does not prove that a third-party process can create the privileged AudioTrack or
that a remote caller hears data. Those require a runtime API probe and an explicitly
authorized live call.
